# 协作开发分支规划

日期：2026-10-24。适用于本仓库的人类协作者、多会话和多 worktree 开发。

建议采用 **一个长期 `main`，每个任务一个短期分支和独立 worktree，多任务按需使用临时整合分支**。版本冻结时再建立发布分支；目前不增加长期 `develop` 或 Web、桌面、Android 平台分支。

本文在规划编写阶段仅形成文档，未执行分支操作或配置远程保护规则；后续提交与合并以用户明确授权和实际执行记录为准。提交、推送、PR、标签和发布的授权边界仍以[根开发规范](../../AGENTS.md)及用户当次明确指令为准；采用本文不等于授权自动执行这些操作。

## 1. 当前基线与选择理由

规划编写时只读核对的本地状态（历史快照，不代表后续执行时的实时状态）：

- `main`、本地远程跟踪引用 `origin/main` 与当前 HEAD 均为 `f37682ba8dc0830fbdaf8de74b54685e7f8b6ce0`。没有执行 fetch，不能据此判断服务器是否有新提交。
- 当前工作树起始时干净，处于 detached HEAD；开始后续代码任务时应先绑定命名分支，避免成果只有游离提交可追踪。
- 本地 14 个命名分支（含 `main`）的提交均已包含在 `main` 中。A—E、界面优化和已有整合分支属于历史任务线，不作为后续任务默认起点。
- Git 登记了 12 个 worktree。其他 worktree 的未提交、未跟踪及忽略文件未完成核实；“分支提交已合入”不能证明可以删除工作树。
- `origin` 已使用 SSH；本次未修改远程配置。

Web 和桌面共用 `apps/web`，平台适配与共享格式也存在依赖。长期按平台分支会增加重复同步和兼容验证成本。现有任务已使用独立提交与整合提交，短期分支能够延续这些追踪、验证和回滚边界。

`main` 的目标是保持可构建、相关回归通过，并满足 Web 发布要求；桌面代码合入 `main` 不代表安装、升级和正式发行已验收。具体剩余项见[桌面说明](../../apps/desktop/README.md)和[双端验证记录](../../test/dual-platform/README.md)。

## 2. 分支类型与生命周期

| 类型 | 命名与示例 | 从哪里建立 | 合向哪里、何时结束 |
| --- | --- | --- | --- |
| 主线 | `main` | 现有分支 | 长期保留，只接收已验证的任务或整合结果 |
| 普通任务 | `codex/<scope>-<topic>`，如 `codex/desktop-window-a11y`、`codex/web-import-cancel`、`codex/android-parser-images` | 已核对的最新 `main` 提交 | 通常合入 `main`；参加联合交付时先合入整合分支；完成后待确认归档 |
| 文档与工程任务 | 同一规则，如 `codex/docs-collaboration`、`codex/ci-web-release-gate` | 已核对的 `main` | 按实际影响完成检查后合入；无需长期文档或 CI 分支 |
| 多任务整合 | `codex/integrate-<batch>`，如 `codex/integrate-desktop-acceptance` | 整合开始时的最新 `main` | 汇集该批任务、解决冲突并联合验证后合入 `main`，随后结束 |
| 发布候选 | `codex/release-<platform>-<version>` | 已选定的 `main` 候选提交 | 仅在需要冻结候选、同时继续主线开发时创建；修复回流主线，发布及后续维护结束后归档 |
| 已发布版本修复 | `codex/hotfix-<scope>-<topic>` | 明确的已发布标签或提交 | 修复目标发布线，同时回流 `main` 和受影响的候选线，验证后结束 |

`scope` 使用 `web`、`desktop`、`android`、`shared`、`ci`、`docs` 等实际范围；`topic` 表达一个可验收目标。一个任务可以跨平台，但不能把无关改动装入同一分支。提交类型通过 Conventional Commits 表达，不必再按个人或会话永久分支。

已有 `codex/dual-platform-stage-*` 等名称保留，不为统一命名改写历史。不提前创建空任务分支；在任务范围、起点和负责人明确后创建即可。

仅当团队确实需要长期独立集成环境或持续维护多个已发布版本时，再评估增加长期开发线或维护线。发布版本号、标签格式应在实际发布任务中核对，本规划不新增版本体系。

## 3. 每个任务的协作约定

开始任务时，在任务说明或对应实施计划中记录：

| 项目 | 必须说清的信息 |
| --- | --- |
| 目标与边界 | 预期行为、验收条件、明确不包含的工作 |
| 负责人 | 一名任务负责人；多任务交付另指定一名整合负责人 |
| 分支与位置 | 分支名、独立 worktree 路径、基线提交 SHA |
| 依赖与改动范围 | 前置任务/提交、主要文件、共享文件协调人 |
| 设计与验证 | 已批准的设计入口、适用命令、人工验收和环境缺口 |
| 交付记录 | 已授权提交的 SHA、验证所用 SHA、未完成项、目标分支 |

一条活跃任务分支对应一个 worktree。不同任务分别安装和使用各自依赖、构建目录与测试 profile；不同时改同一工作树。主 `main` 工作树保持干净，用于接收已经验证的整合结果。

跨模块功能、IPC、数据格式、安全边界或产品选择仍先走设计确认；规划分支不会替代设计授权。普通 Bug 先补回归，纯文档按文档检查交付。

存在依赖时，优先等前置任务合入 `main` 后再建立后续分支。如果必须提前并行，应记录前置任务的具体提交，从该提交建立依赖分支，并先用既定契约或 fake 实现验证；最终按依赖顺序合并，不把尚未合入的前置任务藏在后续任务里。

## 4. 并行分工与冲突热点

| 工作面 | 主要位置 | 协调方式 |
| --- | --- | --- |
| Web/桌面共享业务 | `apps/web/app.js`、`index.html`、共享样式与 `platform/` | 按导入、练习、备份等行为切片；同一函数或状态流转同一时间只由一个任务修改 |
| 桌面视觉与窗口 | `apps/desktop/frontend/`、窗口配置 | 可与独立 Android 任务并行；涉及资源生成器、共享导航或权限时提前协调 |
| 桌面数据与网络 | `apps/desktop/src-tauri/src/` | 按存储、文件、凭据、网络模块分工；IPC、迁移和关闭流程由相关任务共同核对 |
| Android 原生 | `apps/android/` | 可独立推进；题库格式、答案和图片语义变化需同步共享 fixture 与跨端验证 |
| CI、打包与文档 | `.github/workflows/`、桌面脚本、规范与验证记录 | 由明确任务维护；其他任务提供结果，避免同时改总计划或总验证表 |

共享高冲突文件包括 `apps/web/app.js`、`apps/web/platform/contracts.d.ts`、`apps/desktop/frontend/adapter.js`、Rust 的 `lib.rs`/`commands.rs`、`tauri.conf.json`、`scripts/prepare-web.mjs`、依赖清单与锁文件。多个任务需要修改时，先约定契约和先后顺序；只改变分支名称不能消除这些冲突。

公共契约可以先以一个完整、可验证的小任务合入，再并行实现各端。为满足分支隔离，不复制第二份共享业务源码；`apps/desktop/dist` 继续由生成器维护。Android Web 壳的历史 assets 不因 Web 变更自动同步，是否同步须属于明确任务范围。

同一 worktree 内，`prepare:web` 与依赖 `dist` 的 Rust 编译、测试、打包串行执行，避免生成时文件被另一进程读取。GUI 验收和性能测量也应安排独占时段，避免窗口焦点和负载互相干扰。worktree 不会自动隔离 Windows 凭据、应用数据或固定服务端口；继续使用项目已有的隔离测试入口。

## 5. 合并与回流流程

单任务在自己的分支完成实现和适用检查，再交付审查；简单独立任务不强制增加整合分支。多个任务共同交付时，采用以下流程：

1. 核对各来源 worktree、未提交改动、任务依赖和目标分支。用户明确要求“合并任务到目标分支”时，才按既有规则获得该次合并所需提交的授权；这不包含 push。
2. 各子任务在自己的分支独立提交，记录来源路径和提交 SHA，不默认复制未提交文件集中提交。
3. 从最新目标分支建立临时整合分支，按“契约/基础能力 → 依赖实现 → 联调”的顺序合并。默认保留 merge 关系，不将多任务成果 squash 成一个失去来源边界的提交。
4. 必须在合并时完成的冲突解决体现在对应 merge 提交中；后续冲突修正、联合测试适配单独提交，不混入或改写原任务提交。
5. 对整合后的完整状态运行受影响检查，记录实际提交、环境、结果和缺口。任务单独通过不能替代联合验证。
6. 合入目标分支前再次确认其未前移。若前移，先把新目标合入整合分支，并重跑受影响验证；不得强行覆盖。目标仍为整合起点时，可将目标快进到已验证的整合提交，保留所有子任务与合并历史。
7. 交付报告列出子任务提交、整合/修复提交、目标分支和验证结果。推送、PR、发布与工作树清理分别按授权处理。

共享分支不通过 rebase 或 force push 改写他人基线。已合入的缺陷通过新的修复或经授权的 revert 处理，不以 reset 重写主线。涉及数据迁移时，代码回退不能直接替代数据兼容与恢复验证。

发布候选冻结期间，普通功能继续进入 `main`，不随意合回冻结分支。候选修复应保持独立提交，及时回流 `main`；仅在完整分支合并会带入不需要的改动时，才选择明确的修复提交并记录原 SHA。维护旧发行版时，不将整个最新 `main` 合入旧版修复线。

## 6. 验证、远程保护与发布边界

检查矩阵以[根规范第 5 节](../../AGENTS.md#5-验证要求)为准。桌面涉及代码时运行 npm 测试、typecheck、lint；Rust 追加 fmt、Clippy 和测试；资源生成、原生或构建变化追加 build。需要桌面运行验证时，先 `npm run build:test`，再 `npm run test:desktop`。共享 Web、Android 和解析器按实际影响追加现有回归。

文档任务执行 `apps/desktop` 下的 `npm run lint:docs`，未列入脚本的修改文件补充 UTF-8、代码围栏、本地链接和差异检查。根目录没有 `package.json`，不在根目录直接套用 npm 命令。

当前仓库配置有两个重要边界：

- [Pages 工作流](../../.github/workflows/pages.yml) 在每次 push `main` 时发布 `apps/web`，没有等待桌面检查成功的依赖。因此，推送 `main` 同时具有 Web 发布效果；只授权本地合并时不能推送。文档提交推送到 `main` 同样会触发该工作流。
- [Windows 工作流](../../.github/workflows/desktop.yml) 对 PR、push `main` 和手动触发执行。单独 push 普通任务分支不会触发这套检查；协作者在获准创建 PR 后使用 PR 检查，或按授权手动运行。CI 的 GUI 验收提示不代表 WebView2、安装升级或 Win10 已验收。

建议后续单独落实以下远程规则；本次未读取远程设置，不能断言它们已经启用：

| 对象 | 建议规则 |
| --- | --- |
| `main` | 禁止直接推送、强制推送和删除；经 PR 合并，要求另一位协作者审查及实际适用的检查通过 |
| 多任务整合 PR | 使用保留合并历史的方式；不要 squash 整个批次，否则丢失独立任务的追踪和回滚边界 |
| 分支更新 | 合并前确认检查覆盖最新目标状态，目标变化后重跑受影响验证 |
| Web 发布 | 在独立 CI 任务中设计检查成功后才部署的依赖，或明确的发布审批；目前仍按现有 push 行为处理 |
| 桌面发布 | 固定已验证提交、版本、制品 SHA-256 和验收记录；正常/离线安装包分开标识，交互式及干净系统验收另行完成 |

若暂时只有一名维护者，使用独立审查会话和验证记录作为本地协作步骤；远程审批人数须按实际可参与的协作者设置，避免设置无人能满足的规则。自动化审查不能冒充另一位人类审查人的批准。

## 7. 建议的下一批任务

下面是可以按需启动的任务边界，不表示全部开发需求已获批准，也不要求一次创建所有分支。

| 建议分支 | 任务范围 | 并行与前置条件 |
| --- | --- | --- |
| `codex/docs-collaboration` | 保存本规划、统一文档入口和任务交接规则 | 规划已形成，提交与合并按用户明确授权执行 |
| `codex/ci-web-release-gate` | 解决 Web 发布与检查相互独立的问题，落实适合团队的合并规则 | 先确认发布方式；可与产品代码任务并行 |
| `codex/desktop-install-acceptance` | 在隔离 Win10/Win11 环境核对新装、离线安装、覆盖升级、卸载保留等剩余项，按发现补修复 | 必须固定候选提交及制品；不操作真实用户数据 |
| `codex/desktop-window-a11y` | 多显示器、DPI、系统拖入、键盘与覆盖层的剩余验收及局部修复 | 可与安装验收并行；共享窗口配置或文件时协调 |
| `codex/desktop-document-stress` | 大文档、复杂公式/图片、多轮内存峰值与释放验证 | 性能测量独占时段；与其他修改共享导入逻辑的任务错开 |
| `codex/integrate-desktop-acceptance` | 汇集本批已确认修复，重新构建并执行联合验收 | 等待相关任务提交后建立；若候选代码改变，重做受影响的发行验收 |

Web 和 Android 的具体新功能按后续明确需求分别拆任务，不为平台各建一条长期开发分支。自动更新、同步模式或存储格式等新能力仍需独立设计，不并入本批验收任务。

## 8. 现有分支与 worktree 的处置

已合入的阶段、界面和整合分支先标记为“历史任务已合入”，停止继续追加无关开发。规划编写时的 detached HEAD 工作树若用于提交本规划，可绑定 `codex/docs-collaboration`，保留现有文件；其他游离工作树须先核对各自任务。

清理前分别确认：任务是否结束、是否还有未提交或未跟踪内容、忽略目录是否含需保留的验收报告/候选包、分支提交是否已被目标包含，以及是否仍有其他会话使用该 worktree。经用户授权后再逐项归档或删除，不因 `git branch --merged` 的结果批量清理。

后续新任务统一从已核对的主线建立，避免继续从阶段 A—E 的历史分支起步。采用本规划不自动授权删除旧分支、修改其他工作树或改变已有提交结构。
