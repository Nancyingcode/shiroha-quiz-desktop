# Windows Tauri 最小原型实施计划

日期：2026-10-23

依据：[已确认的原型设计](../specs/2026-10-23-tauri-prototype.md)。用户本轮明确选择 Tauri 并要求按此前讨论开发最小原型，设计确认已具备，无需再次询问同一选择。

## 1. 实施约束

- 仅新增桌面工程及相关说明，不改动 `apps/web` 和 Android 的业务源码，不覆盖用户已有改动。
- 不引入数据库、原生网络/文件 IPC、自动更新或新的前端框架。
- 使用 npm 管理 `apps/desktop` 工程；新脚本采用具备类型检查的 JavaScript 或 TypeScript，遵守现有禁用 `any`、`var` 等规则。
- 行为实现按失败测试、最小实现、通过测试的顺序推进；对不能自动验证的 WebView2 行为先记录可重复步骤。
- 不擅自 commit、push 或发布。下列任务完成状态以实际结果为准，不因计划已写好而标记实现完成。

## 2. 任务一：确认环境与工程边界

目标：明确能执行哪些验证，避免把环境问题混入实现结果。

1. 读取工作区状态和根规范，记录用户已有未提交文件。
2. 检查 Node/npm、Rust/Cargo、MSVC、Windows SDK 和 WebView2。当前已有 MSVC 与 WebView2 155，Rust 缺失。
3. 选择与 Tauri 2 配套的 CLI/Rust 依赖，使用官方说明核实配置和开发命令。
4. 固定应用标识 `com.yiqiu.shirohaquiz.desktop`；开发端口 `51736` 通过实际 CLI 参数验证。
5. 如需安装依赖，先确认并停止使用该工程依赖的相关进程；不结束无关项目或系统进程。不在未检查环境时执行会重建已有 `node_modules` 的命令。

交付：新工程依赖与命令约定，环境缺口说明。

## 3. 任务二：先验证资源准备脚本的失败用例

目标：在实现资源生成行为前建立可观察的正确性与安全边界。

计划新增资源准备脚本和对应测试，路径位于 `apps/desktop/scripts` 与 `apps/desktop/test`，具体文件名随工程落地。测试使用独立临时 fixture，不修改真实 `apps/web`，不接触用户浏览器数据。

先编写并执行以下用例，确认失败来自尚未实现的行为：

1. HTML/CSS/JS/MJS、媒体、题库和运行库被保留；CMD、PS1、README、source map 被排除；第三方许可证保留。
2. 准备前后来源文件内容相同；重复生成一致；旧生成文件被清理。
3. 内联点击事件被转为本地外部脚本中的监听器，原页面不再包含可执行内联属性，调用保持原有点击与 `this` 语义。
4. 无法安全转换的内联执行形式显式失败。
5. 输出目录越界、来源/输出重叠及链接越界被拒绝，既有无关文件保持不变。
6. PDF module/Worker 与 OCR Worker/WASM/语言包的相对路径保留。

交付：最小相关测试的红色结果；测试必须能识别错误行为，而非仅比较生成器内部实现。

## 4. 任务三：实现资源准备与绿色验证

目标：生成桌面专用资源，同时保持 Web 为唯一业务源码。

1. 实现显式来源、受限目标的资源生成脚本，使用原生文件 API，不拼接跨 shell 删除命令。
2. 在执行任何递归清理前验证绝对目标路径位于桌面工程下，且不会清理来源或链接指向的外部目录。
3. 实现过滤与内联事件转换。生成脚本由可信仓库源码构建，不引入运行时 `eval` 或 `Function`。
4. 对真实 `apps/web` 执行准备命令，检查 PDF、OCR、MathJax 关键文件齐全。
5. 重跑任务二的单个测试文件；全绿后只做必要的局部整理，再次运行受影响测试。
6. 确认 `dist` 与构建输出被忽略；不提交生成资源，也不手工修改生成文件。

交付：`npm run prepare:web` 可重复生成资源，相关自动化用例通过，Web 源码无变化。

## 5. 任务四：新增最小 Tauri 应用壳

目标：在独立 Windows 窗口中加载已准备的资源。

1. 在 `apps/desktop/src-tauri` 添加 Tauri 2 最小应用入口、构建配置及窗口配置。
2. 设置固定 identifier、应用名称和 `frontendDist`；不添加原生业务命令或无关插件。
3. 使用 CLI 内置开发服务，不新增自定义 HTTP 服务。`beforeDevCommand` 等待资源准备结束；核实 `--port 51736` 的有效性。
4. 添加生产 CSP，允许实际需要的本地脚本、Worker、WASM、图片和样式；阻止远程脚本执行与内联 JavaScript。
5. 保留浏览器 AI/WebDAV 请求所需的 HTTP/HTTPS 连接，但不开放原生 HTTP、文件系统、shell 或任意进程能力。
6. 建立可重复的结构与资源检查，验证安全配置没有随适配被意外放宽。

交付：最小应用壳、开发/构建入口、类型检查和 lint 配置。正式签名、安装器分发及自动更新不在本阶段扩展。

## 6. 任务五：桌面兼容验证

目标：核实关键能力实际运行在目标 WebView2 中，而非仅能打包。

准备无敏感内容的隔离样本：小 JSON 题库、文字 PDF、少量扫描页 PDF，以及必要的公式/DOCX/XLSX 样本。原型兼容验证步骤如下：

1. 运行开发命令，确认生成完成后出现独立窗口，导航与小题库练习正常。
2. 构建并启动 release 可执行文件；用测试题库验证关闭重开后的数据保留，不把开发来源数据当成生产数据。
3. 导入文字 PDF，检查本地 PDF.js module 与 Worker 的网络和控制台结果。
4. 阻断外部网络后运行小规模 OCR，检查本地 Blob Worker、WASM、语言包以及逐页识别进度。
5. 检查公式、DOCX/XLSX 的解压和内容显示，以及现有备份/文档导出是否在桌面窗口中可用。
6. 验证生产来源无法执行 CDN 脚本或内联 JavaScript，不因资源加载失败关闭 CSP。
7. 遇到只在 WebView2 中可观察的问题，记录输入、操作、错误和预期，再做最小修复；有稳定复现方式时补自动化回归。

Rust 不可用时，继续完成资源、类型、lint 和可运行的浏览器验证；Tauri 编译和 WebView2 验证明确标记为受环境阻塞，不将浏览器结果替代桌面结果。

## 7. 任务六：完整门禁与交付说明

在 `apps/desktop`，以最终 `package.json` 为准执行：

```powershell
npm test
npm run typecheck
npm run lint
npm run build
```

`lint` 包含对本次新增 Markdown 的 UTF-8、代码围栏和本地链接检查。若仓库尚无对应脚本，只新增满足本工程和本次文档需要的检查，不对历史文档进行无关修复或批量格式化。

交付说明包含：

- 从项目目录启动开发与构建的确切命令及前置条件。
- 生成资源与唯一 Web 源码的关系、固定应用标识和开发/生产数据差异。
- 当前使用 localStorage，浏览器 CORS 和原有容量限制仍存在。
- 所有门禁的实际结果；Rust、MSVC 或 WebView2 缺失导致的未执行项目单列。
- PDF/OCR 是实际离线 WebView2 通过、仅浏览器通过，还是仍待验证。
- 未完成的原型兼容项及明确原因，不声称已完成正式发布。

最终检查变更差异、Markdown 结构和链接，确认没有误改 Web、Android 或用户文件，再向用户报告实现和验证状态。
