## 3. 分步实施

以下复选框保留原计划；实际完成与验证情况以第 6 节的实施记录为准。

### 步骤 1：先固定失败回归

- [ ] 先阅读 JavaScript 适配指南、Rust 风格指南及相关现有源码和测试。
- [ ] 在现有 Harness 隔离测试中构造新进程快照：已保存 Codex 配置、本地组件存在、订阅尚未核验、设置页未激活。
- [ ] 补充失败用例：应用启动后应主动检查并发布就绪通知；不进入设置页也可更新 AI 入口。
- [ ] 加入 CodeBuddy 在账户卡片早于或晚于执行配置初始化时的用例，证明已有组件及 CLI 账户仍应恢复就绪。
- [ ] 证明直接 API 启动不发模型探测、不检查其他提供方，缺配置仍引导设置。
- [ ] 检查 fake IPC 调用记录，断言没有 `harness_execute`、下载、登录、提供方切换或秘密写入；记录修复前失败原因。

先运行与新增用例相邻的最小测试，确认失败来自当前缺口，再实现行为。

### 步骤 2：实现有界的原生就绪检查

- [ ] 先添加 Rust 失败测试，再在 `harness_control` 的控制枚举中增加 `check_readiness { id, revision, confirmedAfterRestore }`；验证 UUID、当前配置修订与已保存 Harness 模式。恢复确认标记仅由用户主动重试时使用。
- [ ] 从现有受管组件准备逻辑抽取或复用本地检查部分。Codex 使用已保存来源，CodeBuddy 使用固定受管位置；缺失、损坏、越界链接或文件锁失败均不能进入下载或替换路径。
- [ ] 本地组件成功后复用现有 Codex 订阅或 CodeBuddy CLI 账户核验；只在来源、配置和账户仍一致时更新当前状态。保持 `status` 只读快照语义。
- [ ] 检查由请求 ID 标识并受现有独占、取消、授权清理和数据恢复屏障保护；旧结果不能解除清理失败或停止未确认状态。
- [ ] 用具名常量落实 30 秒整体上限；覆盖本地校验和认证等待，取消时确认检查终态并释放本次资源。
- [ ] 覆盖有效缓存、未登录、账户过期、错误来源、文件损坏、网络失败、超时、取消、修订变化、恢复屏障和迟到结果。

使用合成小文件、假进程与 mock 账户服务验证控制流。固定生产摘要和已有隔离执行边界继续由现有回归验证，不读取本机真实账户，也不因测试需要放宽生产校验。

### 步骤 3：实现共享检查协调与启动接线

- [ ] 先补去重和生命周期失败测试，再在 `HarnessApi` 添加 `ensureReady()`、`retryReadiness()` 及共享快照中的可选检查状态字段；保持原 `ready` 判定来源。
- [ ] 同一窗口当前生命周期只保留一个检查 Promise；成功复用，失败等待明确重试，连续点击重试不并发。
- [ ] 在首次应用数据加载成功、事件绑定完成且普通交互已解锁后调用检查。检查失败只更新 AI 区域，不将整个应用切换为数据恢复错误。
- [ ] 进入设置页、账户卡片刷新与请求前置检查复用协调入口，消除设置页激活和初始化先后的依赖；普通渲染不再次核验。
- [ ] 保存新配置或切换账户时作废旧检查并按当前已保存选择核验；表单草稿不影响活动路由。
- [ ] 将冷启动与恢复、重置后的初始化明确区分；恢复后保持阻塞，只有用户显式刷新才能重新接入，保留下一次全新启动的检查能力。
- [ ] 超时取消本次 ID 并确认停止；不能确认终态时保留阻塞，旧检查收敛前禁止重试。窗口关闭释放本窗口监听和计时器。

CodeBuddy 账户卡片只共享首次主动核验与重试，仍通过既有观察机制及时报告 CLI 退出和账户变化，不能用旧卡片状态恢复原生已撤销的授权。

### 步骤 4：统一页面状态并补齐局部刷新

- [ ] 先添加状态到文案和按钮行为的回归，再实现按任务的统一可用性计算：检查中、可用、未配置、需处理、检查失败、不支持和受阻。
- [ ] 替换各面板将不可用直接解释成“未配置”的分支；保留 CodeBuddy 导入与批量限制，直接 API 不标注未经验证的连接成功。
- [ ] 检查中保留功能位置并暂时禁用生成，结束后原地恢复。失败提供键盘可达的“重试检查”，真正缺配置或需登录时引导设置。
- [ ] 复用现有局部更新接口覆盖练习、错题、收藏、考试结果、训练复盘、导入和批量面板；不通过整页重建刷新状态。
- [ ] 对请求前置检查与点击交错补回归：等待完成后重新取执行快照，业务会话或输入变化、切题、离页与取消均不继续发送旧请求。
- [ ] 验证保存草稿、追问、停止、重新生成及人工采纳行为保持原语义；后台完成不自动生成、不重复发送。
- [ ] 检查状态播报、焦点、窄屏和现有页面样式；仅在现有样式无法承载时添加最小样式，不引入组件框架或动画。

### 步骤 5：联合回归与桌面运行验证

- [ ] 使用隔离 fixture 打开未进入设置页的各个 AI 页面，延迟返回检查结果，验证当前面板无需重新导航即可使用。
- [ ] 新建桌面测试进程，验证已有组件与假账户的首次启动、关闭后重开；不能用同一前端上下文重复初始化替代进程重启。
- [ ] 验证直接 API 的练习、训练复盘、导入与批量既有回归，以及缺配置跳转设置后的答题状态保全。
- [ ] 确认检查阶段模型调用为零、组件下载为零；只有用户主动生成后才有一次相应模型请求，失败后不自动重发。
- [ ] 执行下节适用门禁，记录通过数量、实际环境和缺口。仅在失败或后续改动影响结果时重跑对应检查。

## 4. 验收矩阵

| 场景 | 预期 |
| --- | --- |
| Codex 已配置、现有组件及订阅有效，设置页未进入 | 后台核验后当前页面可用；不要求先打开设置 |
| CodeBuddy 组件及 CLI 登录有效，不同初始化顺序 | 单题与追问可用，导入与批量仍受能力限制 |
| 直接 API 配置完整或配置缺失 | 分别保持已配置或引导设置；启动模型调用为零 |
| 组件不存在、损坏、自定义路径失效 | 保留配置和文件，引导设置准备或修复，不自动下载或切换来源 |
| 账户未登录、已过期、清理失败或格式不兼容 | 显示实际原因，遵循现有登录及清理流程 |
| 网络失败、检查延迟、30 秒上限、显式重试 | 状态准确，普通业务可用，重试去重且旧结果不覆盖新状态 |
| 页面已打开且包含草稿、答案或追问 | 原地更新 AI 状态，保留内容与交互；后台完成不发送题目 |
| 检查期间切题、离页、取消、保存配置或换账户 | 原上下文失效，不继续发送旧请求或恢复旧授权 |
| 恢复题库、重置、退出失败与停止未知 | 保留现有阻塞；同进程普通初始化不自动重新接入 |
| 同时进入设置、点击重试或发生卡片状态通知 | 仅一个在途检查，不重复认证或执行模型 |
