# CodeBuddy 自有适配层补救研究

日期：2026-10-25。状态：适配层 P0 已完成；用户在说明具体原生方案及仅内存登录后回复“继续”，已确认下述增补设计。原生实施见[实施计划](../plans/2026-10-25-codebuddy-native-adapter.md)，研究实测范围见[验证记录](../plans/2026-10-25-codebuddy-adapter-p0.md)。

## 问题和目标

前轮[直接管道试验](../plans/2026-10-25-codebuddy-cli-stdio-p0.md)发现本地 Gateway、结束信息丢失和额外请求。本轮不将这些现象一律交给上游处理，验证我们能控制的边界：任务结果一致性、模型流转发、一次性上游预算和原生网络隔离。

初始 P0 研究保持现有 Codex、直接 API、正式 IPC 和持久化格式不变，只使用固定 EXE、假凭据与合成题目，不登录真实账户、不消费积分、不修改厂商包。随后用户批准原生方案、真实个人账户验证及独立登录入口，范围见下方增补；正式模型执行仍须完成独立验收。

## 可行性假设

1. stdout 适配层核对同轮流文本、最终 assistant 与 result，拒绝工具、额外模型回合、取消、重复或不完整结果。它不能恢复已经丢失的信息：归一化随机字段后，正常 stop、EOF、只有 `[DONE]` 的完整事件序列相同。
2. 显式配置模型 BASE_URL 指向自有转发层，在转发层先确认唯一 choice、完整 SSE、`finish_reason=stop` 和 `[DONE]`，再允许结果进入业务。首次转发前占用本任务预算，后续请求本地拒绝，不再触达上游。转发层只允许固定路径和模型，不是通用代理。
3. 转发层与 CLI 之间使用本次任务随机能力值；正式实现不允许前端传入任意地址/命令。真实官方请求仍保持证书校验与目的地址限制，不安装全局 CA 或把 HTTPS 诊断日志当成稳定契约。
4. 自有转发层并不自动隔离 CLI 的 HTTP Gateway。Windows AppContainer 同容器通信和宿主访问限制需要独立验证，不能拿随机端口、反向代理或 Job Object 冒充网络隔离。
5. 直接启动 CLI 并显式保持内存凭据有望避免 SDK 强制文件存储，但真实订阅登录、刷新、模型地址覆盖顺序和注销仍须验证。假 Key 路径不等于同账号积分通道。

## 正式接入前的决策

仅在转发层出口不可旁路、CLI 的本地服务满足已确认威胁模型下的隔离要求、凭据有受保护生命周期、账户计费通道已确认时，才可进入正式 Harness。AppContainer 对容器外直接访问的限制不能表述为禁止所有其他进程访问，同 SID 例外见下文。若需要独立容器、管理员服务、不同最低 Windows 版本或改变登录保持体验，应明确成本与兼容范围后请求设计确认。

## 建议的正式实现增补（已确认）

### 1. 普通桌面威胁模型下的候选

推荐继续研究“原生宿主 + AppContainer 内受控执行器/转发组件”。目标是阻止容器外程序直接调用 CLI 未认证本地接口，并让题目、凭据与上游请求经过本应用明确授权的业务通道。**不承诺抵御已经能以同一用户运行任意原生代码、主动派生同 SID 或读取本应用内存的攻击者。** 实测证明同用户程序可以加入已知 SID，随机 profile 名不是可靠秘密。

若必须抵御上述主动同用户程序，应改用独立账户、虚拟机或受信服务等更强边界，属于不同的安装、运维及兼容成本，不能把当前 AppContainer 方案包装成等效能力。

### 2. 原生实现范围

- 继续复用现有 Rust/Windows Job、哈希校验、任务 revision、恢复屏障和人工采纳流程。候选转发逻辑独立成模块，不扩张前端为通用 HTTP/进程客户端。
- 生产中不默认引入 Node、Python、官方 SDK 或 C# fixture；研究代码用于验证规则。优先用项目现有 Rust 依赖实现内部 worker/转发组件，具体二进制入口及 IPC 需在实现计划中固定。
- CLI 使用专用 AppContainer、私有目录和有限继承句柄，不默认授予互联网 capability；只让受控网络组件访问固定官方目的地址。跨进程控制使用继承管道或受限 IPC，参数、token、能力值不放命令行或测试 ready 文件。
- 子进程创建失败、隔离无法建立、组件哈希不符、网络路径不明确时拒绝运行，不退回普通进程。Bun 临时目录必须显式放入受控目录；不扩大系统根目录 ACL、不设置全局回环豁免。
- 模型响应先在原生转发层完整缓冲验证，再交 CLI 处理；首期不向 UI 展示未校验增量正文。代价是失去逐 token 展示，现有单题/导入候选流程仍可保持。
- 单任务一个预算和一份私有完成证明，转发前占用，失败不释放后自动重发。取消同时中止 CLI、转发连接与证明，关闭/恢复后迟到结果失效。

### 3. 凭据与订阅阶段

本轮假平台 Token 已通过 Bearer 路径，但这不是正式订阅验收。下一阶段先明确受控登录运行时与无互联网执行运行时如何交接内存授权、如何获取固定模型配置，并验证真实官方请求是否仍保留国内个人账户身份。

首期采用仅内存登录，退出应用清除，过期无法安全刷新时要求重新登录，不将明文授权写到磁盘。登录、刷新、401、退出和进程重建各有状态；不能把 SDK 原有自动持久化直接打开。是否保留长期登录另行设计受保护存储，不在本阶段顺带引入。

网络组件对模型路径和认证路径分别建白名单；不提供任意 CONNECT/HTTP 转发，否则可能为 `/v2/service-proxy` 等业务重新打开出口。若 CLI 官方认证只能经不可检查的通用代理，必须先重新评估安全边界，不以“只允许同域名”代替路径约束。

### 4. 分阶段实施与停止条件

1. 把本轮转发校验与 AppContainer 启动移植为原生内部原型，先使用相同假服务，补充进程树、取消、资源释放、真实出站禁止与跨任务证明隔离。
2. 验证官方国内登录和固定模型的受控网络路径，不启用产品下拉选项；明确重启与过期重新登录的体验。任何任意出口或明文凭据落盘均阻止后续阶段。
3. 在用户主动登录后做限定的账户/积分核对，再连接测试、单题解析与追问；完整 P0 通过后才扩展公共配置、保留 Codex/API 并加入正式入口。
4. 执行项目原生/桌面全部适用门禁及 Win10/Win11、代理、恢复、升级验收。当前本机 P0 不替代这些检查。

确认项是上述威胁模型、仅内存登录和新的原生隔离执行组件，而不是要求接受已知的终态误判或开放任意本地接口。

## 客户端登录入口增补（用户已授权）

用户明确要求“完成登陆入口后再结束任务”，本次把已验证的个人账户登录接入 Shiroha 的 AI 设置。采用独立的 CodeBuddy 账户区域，提供登录、打开当前授权页、复制链接、刷新、取消和退出；账户登录不修改现有 API/Codex 执行配置。真实模型只执行过一次连通性请求，因 `length` 终态被拒绝，服务端 usage 报告总计 151 token，后续单题与追问未运行；因此此阶段只开放账户连接，并清晰显示模型执行尚未开放。该 usage 不代表已核对积分扣减。

新增受控业务 IPC `codebuddy_control`，仅允许主窗口本地来源与固定动作，不接受 URL、路径、令牌或模型正文。`login` 必须携带界面已确认的 `revision`，原生端只接受与当前修订相等的请求；`status/open_login/cancel/logout` 只接受 `kind`。取消、退出和开始新登录都会递增修订，使尚未开始的旧登录请求和已在运行的旧任务都失效。

状态只返回 `phase/revision/loginUrl/message/browserOpened/busy` 六个字段，不返回 uid、昵称或令牌；`phase` 限定为 `signed_out/authenticating/signed_in/expired/failed/cancelled`，登录链接仅在等待授权时公开。同次登录可以在同一修订更新为终态；前端同时检查页面 generation、请求序号和修订，拒绝迟到结果。只在等待授权时轮询，取消、退出和终态会清除链接并停止轮询。

原生组件复用固定官方认证客户端，自动打开经过 challenge 校验的授权 URL；重开动作只读取原生持有的当前 URL。网络等待和系统浏览器派发都不持有登录状态锁，取消与退出不等待浏览器返回。已交给系统的打开请求可能稍后才显示页面，但返回结果只有仍属于当前修订时才能更新状态，不会恢复旧授权。

会话、challenge 和取消标记只属于当前进程；退出登录主动失效内存会话，关闭应用后需要重新登录，过期检查也会清除会话。本阶段不把授权写入文件、数据库、备份或凭据管理器，也不自动刷新令牌。Web 端隐藏账户区域；隔离 native-test 构建采用合成身份，不打开真实浏览器或访问真实账户。界面使用现有设置样式、语义按钮与 aria-live 状态，授权页打开失败时保留复制/重开操作。账户入口不自动开始模型请求。

登录入口实现、release 构建与隔离桌面冒烟已完成，真实客户端已显示账户卡片并启动官方授权页；本次客户端授权终态仍待用户手动完成。完整检查与启动证据见[登录入口最终验证记录](../plans/2026-10-25-codebuddy-native-adapter.md#登录入口最终验证记录)。这些结果不改变真实模型尚未通过验收的结论。

## 模型响应兼容研究增补

用户再次要求推进模型执行并解决自有层阻断，继续按已确认原生边界实施。宿主仍先验证完整原始 SSE，但通过后只向 CLI 转发由宿主构造的纯文本 SSE。证明的正文必须来自原始 `content`，最终 CLI 候选必须与其完全一致；不能把 reasoning 当答案，也不能通过规范化隐藏工具调用、拒答、截断或 EOF。

兼容规则按字段值与类型收窄：`role` 仅缺失、null 或 assistant；`content` 和 `reasoning_content` 仅缺失、null 或字符串。推理内容仅在有界响应验证期间读取，不进入 CLI、候选或日志。`tool_calls` 仅缺失、null 或空数组；`function_call` 仅缺失或 null；`refusal` 仅缺失、null 或空字符串。非空工具/拒答、错误类型、未知 delta 字段仍拒绝。仍要求唯一 choice、同一 completion ID、非空正文、唯一正常 stop 与随后的 `[DONE]`，结束后不允许新正文。

提高显式探针的过小输出预算只能减少可避免的截断，不把 `length` 变成成功；单任务仍只发送一次上游请求，失败不自动重试。诊断只记录已知字段的类型/是否为空、终态及用量，不记录推理文本、账户标识或未知字段名。真实端点是否产生这些兼容形状须由后续受限验证确认，合成样例通过不替代该证据。

### 固定版本字段语义的进一步兼容

用户明确要求继续研究并修复这些兼容问题。本增补细化上述纯正文边界，沿用原生隔离和请求预算，不扩张正式 IPC。固定 2.175.0 的实现与类型声明支持以下收窄规则，优先于上段首轮字段列表：

- 空字符串 `finish_reason` 视为继续；缺失/null 保持原有语义，最终仍需唯一 `stop` 和其后的 `[DONE]`。其他非空结束原因及错误类型拒绝。
- `function_call` 仅缺失、null 或精确的两键对象 `{"name":"","arguments":""}`。这个对象没有调用名称和参数；空对象、缺键、null 子值、任何非空字符串（包括空白）、未知子键及工具结束原因均拒绝。不能依赖厂商转换器忽略 legacy function_call 的行为来判断成功。
- `reasoning` 和 `redacted_thinking` 仅缺失、null 或字符串；`extra_fields` 仅缺失、null 或只含可选 `signature` 的对象，signature 仅 null 或字符串。这些字段全部剥离，不进入正文、CLI 或成功判定；未知子键、opaque `_meta`、`reasoning_detail` 等结构继续拒绝。
- JSON 对象递归拒绝重复的已解码键，覆盖原始 SSE 和 CLI JSONL，防止后一个空字段遮盖前面的工具调用、拒答或异常终态。
- 正文仍逐片拼接并保全，不凭末尾相等或前缀关系去重。没有明确的快照契约时，去重会改变合法正文。

这些规则有固定厂商包与合成行为证据，不代表已识别上一真实响应中唯一未知字段的名称，也不能改判那次请求成功。真实响应验收仍需使用新版脱敏诊断独立确认。
