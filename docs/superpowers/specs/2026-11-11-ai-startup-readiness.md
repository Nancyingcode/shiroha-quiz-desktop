# AI 启动就绪检查设计

日期：2026-11-11。状态：用户已确认设计并要求实施；实现与验证进度见实施计划。

实施计划见 [AI 启动就绪检查实施计划](../plans/2026-11-11-ai-startup-readiness.md)。

## 1. 问题与已核对事实

用户反馈：系统开机后首次打开软件，若没有进入“AI 设置”，其他页面的 AI 功能会提示前往设置；进入设置后即可使用。

实施前的源码存在与此现象一致的启动缺口：

- [应用启动](../../../apps/web/app.js)读取学习数据和凭据，再调用 Harness 初始化；[桌面执行层](../../../apps/desktop/frontend/harness.js)的 `initialize()` 只执行 `status` 查询。
- [原生 Harness](../../../apps/desktop/src-tauri/src/harness.rs)在新进程中将 Codex 的订阅确认状态初始化为未确认，`status` 只返回快照，不核验已有登录。CodeBuddy 的组件就绪状态同样需要在当前进程重新确认。
- Codex 的自动检查位于设置页的 `activateRuntime()`，由当前“AI 设置”页面处于活动状态等条件触发。其他页面读取共享快照时，可能一直得到 `ready: false`。
- [共享 AI 设置逻辑](../../../apps/web/ai-settings.js)用布尔值判断可用性；[解析面板](../../../apps/web/ai-question-panels.js)等入口有将不可用统一显示为“尚未配置”或“前往 AI 设置”的分支。
- [CodeBuddy 账户卡片](../../../apps/desktop/frontend/codebuddy-login.js)另有账户读取与自动刷新流程，需要与启动检查协调，避免设置页是否挂载或读取先后决定可用性。

本会话已用假原生响应和隔离 JavaScript 上下文复现：设置页未打开时仅调用 `status` 且不可用；进入设置页后调用 `inspect` 并就绪。尚未执行系统重启、真实账户或安装版验收，不能据此把问题限定为仅在系统开机后出现。

## 2. 目标与范围

1. Windows 桌面启动后，自动核验已保存执行方式所需的现有组件与账户；已配置且仍有效的用户无需先进入设置页。
2. 练习单题、错题与收藏、考试结果、训练复盘、导入整理和批量处理共享相同的可用状态，并按各提供方实际支持的任务展示入口。
3. 检查期间和失败后显示具体状态，避免把“尚未核验”“网络失败”解释成“未配置”。
4. 核验在后台进行，普通题库、练习、记录和本地数据操作可以继续。
5. 沿用现有执行方式、模型选择、认证来源、任务取消、人工确认与备份边界；不增加依赖或改变持久化格式。

本轮不实现新的提供方、自动登录、启动模型测试、自动下载或更新组件。AI 题目请求仍由用户主动触发。MinerU、OCR 和 WebDAV 不纳入 AI 就绪检查。

## 3. 启动流程

### 3.1 公共顺序

1. 沿用现有本地数据、凭据和执行配置读取流程。数据加载失败时进入现有恢复界面，不启动 AI 检查。
2. 初始化界面、绑定现有状态变更回调并解除普通业务交互锁。
3. 根据已保存的执行方式启动一次后台就绪检查。检查使用活动配置，不能采用设置表单中尚未保存的选择。
4. 检查中、成功或失败均发布状态变更，更新当前可见的 AI 区域；不跳转设置页，不改动题目与答题状态。

设置页继续显示配置和诊断，进入设置页时复用当前检查结果。原有用户明确进入设置后的组件准备流程仍按既有设计运行，不能由普通页面渲染顺带触发。

### 3.2 按执行方式检查

| 执行方式 | 启动检查 | 就绪与失败语义 |
| --- | --- | --- |
| 直接 API，含 Web | 恢复已保存地址、模型及现有凭据状态；不向配置地址发探测请求 | 沿用地址与模型的配置判断；API Key 是否必需仍由具体服务决定。“已配置”不表示已经联网验证成功 |
| Codex Harness | 只校验已保存来源的本地组件，再复用现有订阅状态核验 | 组件有效且订阅确认后就绪；缺组件、登录缺失或清理未完成时显示对应处理入口 |
| CodeBuddy Harness | 只校验固定受管目录已有组件，再复用独立 CLI 账户来源与现有账户核验 | 组件和账户均确认后才就绪，返回当前 `accountRevision`；仍仅支持连接测试、单题解析和追问 |
| 尚未接入的 Harness | 读取配置并显示现有能力限制 | 不启动其他提供方，不切换到直接 API |

直接 API 未记住的凭据在进程退出后失效，保持现有语义；本设计不将其改成持久保存。CodeBuddy 核验可能访问既有账户认证服务，仅传该认证协议需要的信息，不发送题库、题目、答案或学习记录，不调用模型接口。

## 4. 组件与原生边界

当前 `prepare_runtime` 在缓存缺失时可能下载组件，不能直接用它实现启动时的本地检查。新增检查应复用现有路径、文件锁、版本、大小与摘要校验，将“检查已有文件”与“用户主动准备组件”分开。

在已有受控 `harness_control` 中增加固定业务动作 `check_readiness`，请求包含本次 UUID `id`、已读取的配置 `revision` 和默认关闭的 `confirmedAfterRestore`，返回现有 Harness 状态结构。只有用户主动重试 Codex 恢复确认时前端才将该标记设为真；原生端在核验成功且请求仍有效后才解除进程内的恢复确认要求。

- 原生端按已保存的活动模式、提供方与来源决定检查对象；前端不能传可执行文件路径、下载地址、目录、账户令牌或命令行参数。
- 仅允许已保存的 Harness 模式。Codex 校验已授权的自定义路径或既有受管路径；CodeBuddy 只检查固定受管位置。不搜索 PATH、不自动切换来源、不下载、不解压、不修复或覆盖损坏文件。
- 组件检查成功后调用既有认证核验服务。Codex 复用 `inspect` 的验证实现；CodeBuddy 复用现有 CLI 来源、账户修订及认证边界，不读取 Codex 应用或其他产品账户。
- 复用现有任务所有权、取消与恢复屏障。`id` 必须归本次检查所有，可使用现有按 ID 取消能力；配置修订、模式、提供方或账户变化后，不接受旧结果。
- `status` 保持快照查询，不因渲染或轮询启动认证。新动作可以更新现有验证元数据和修订，但不修改执行方式、模型选择或登录保存策略。
- 原生整体检查采用具名常量控制 30 秒上限，覆盖本地校验和账户核验；沿用更短的既有子步骤时限。前端使用对应上限，超时取消该检查并确认终态，不以超时为由直接开放执行。
- 缺文件与文件损坏均保留原配置和现有文件，提示进入设置准备或修复。退出清理待完成、停止状态未知及进行中的恢复屏障不能通过检查解除。

不增加 Tauri 命令权限，不开放通用文件、HTTP、SQL 或进程接口；新动作仍按现有主窗口和本地来源限制执行。秘密只在原生既有认证边界内流转。

## 5. 共享状态与页面表现

在 [共享 AI 设置模块](../../../apps/web/ai-settings.js)增加统一的按任务可用性计算，供现有布尔判断和页面展示复用。`ready` 仍由原生或现有 API 配置规则决定；只额外记录当前检查的阶段与固定诊断，不再保存第二份独立的“已登录”或“已就绪”业务状态。

| 可用状态 | 显示与操作 |
| --- | --- |
| 正在检查 | “正在检查 AI 状态…”；保留 AI 功能位置，生成按钮暂不可用，完成后原地恢复 |
| 可以使用 | 显示原有 AI 操作；直接 API 使用“已配置”等现有语义，不显示未经验证的连接成功 |
| 未配置 | 说明缺少地址、模型或执行配置，提供“前往 AI 设置” |
| 需要处理 | 说明组件缺失、组件校验失败或需登录，提供“前往 AI 设置”；CodeBuddy 登录仍由独立 CLI 完成 |
| 检查失败 | 显示脱敏原因，提供“重试检查”，保留设置入口；网络失败不得显示为已退出或未配置 |
| 能力不支持 | 显示当前提供方对此任务的限制；就绪检查成功也不能开放不支持的导入或批量操作 |
| 当前受阻 | 显示任务忙碌、恢复后需重新确认或授权清理未完成等现有原因，按原有恢复方式处理 |

任务能力限制优先于普通就绪提示，例如 CodeBuddy 的批量按钮仍显示不支持。检查过程不能把现有 AI 任务状态改成“生成中”，也不清空已生成的草稿、对话、错误详情或待保存结果。

状态变更除更新导入和练习面板外，还须刷新已有错题、收藏、考试结果及训练复盘中的解析区域。复用局部更新入口，避免重新开始练习、重载整条训练记录或丢失焦点与输入。

状态文本使用现有中文文案风格；检查和错误区域提供 `role="status"`、适当的 `aria-live` 与 `aria-busy`。重试按钮可通过键盘访问，后台完成不抢焦点。

## 6. 去重、重试与生命周期

- 当前窗口同一配置与账户生命周期只维护一个在途检查 Promise。启动、设置页和请求前置检查共享它；检查完成后复用结果，普通渲染不重复发起。
- 平台接口提供 `ensureReady()` 与 `retryReadiness()`：前者复用在途或已完成状态，后者只由用户明确重试触发；点击多次仍只运行一次。检查状态通过共享快照中的可选检查字段呈现，并同步 [平台类型](../../../apps/web/platform/runtime.d.ts)。
- 生成入口在检查中暂不可用；请求层仍复用同一前置检查以处理点击与状态变化交错的情况。等待后重新取得执行快照，核对原业务会话、题目、来源、配置和账户；已经切题、离页、取消或修改请求输入时不继续发送。
- 检查成功不自动生成题目解析、不重放此前失败任务。模型调用开始后的超时、取消、额度或结果未知继续按现有流程处理，不以“重新核验”为由自动重发模型请求。
- 检查失败后停在可重试状态，不增加无限轮询或固定延迟重试。重试只检查当前选择，不修改其他提供方账户。
- 保存执行方式、切换提供方或账户、取消、退出登录、清除配置和窗口关闭使旧检查失效；使用现有 generation、查询序号、配置修订和账户修订共同拒绝迟到响应。
- 已确认保存的新 Harness 选择可发起该选择的一次检查；未保存表单不改变业务路由。正在运行或停止的任务继续由原有互斥规则保护。
- 同一进程中的题库恢复或数据重置作废旧检查并保持 AI 不可执行，不能把通用 `initialize()` 或页面重载当成冷启动而自动重新接入。Codex 的恢复确认保存在当前原生进程内；只有用户显式重试检查或主动检测组件并完成核验后才解除。CodeBuddy 继续使用其独立的账户恢复屏障。下一次全新进程启动可以按已保存选择检查。
- 超时先终止本次检查，无法确认停止时保持阻塞，提供明确提示；旧检查未收敛时不启动另一个检查。

CodeBuddy 账户卡片保留显示、登录指引及既有失效观察；选中提供方的首次主动核验和重试由共享检查协调，卡片事件只同步状态，不能再各自启动重复核验或凭旧缓存恢复就绪。直接 API 或 Codex 活动时，不因隐藏卡片读取而主动核验 CodeBuddy 账户。

## 7. 与现有设计的关系

- 延续 [AI Harness 设计](2026-10-24-ai-harness-execution.md)的统一执行、订阅认证、任务能力、结果校验及取消规则；新增的只是冷启动检查入口和准确的不可用展示。
- 延续 [组件自动管理设计](2026-10-25-managed-codex-runtime.md)中“初始化不启动下载”的边界；进入设置后的主动准备仍保留。已有组件的本地检查允许在冷启动后台进行。
- 延续 [CodeBuddy CLI 共享登录设计](2026-11-04-codebuddy-cli-auth.md)中选中提供方才核验、只读 CLI 来源、恢复后需显式刷新、任务租约与账户修订的规则。
- 不更改题库、记录、备份或凭据格式，不迁移登录，不把就绪结果持久化为跨进程可信凭证，不改变 CSP、代理或服务证书策略。

## 8. 验收标准

1. 隔离桌面进程已有有效 Codex 配置与登录时，不进入设置页，练习、错题、收藏、考试结果、训练复盘、导入及批量入口在后台检查后可用。
2. CodeBuddy 已有有效组件和 CLI 登录时，单题与追问可用；导入和批量仍显示能力限制。组件或账户卡片初始化顺序不影响结果。
3. API 模式恢复原设置，启动时不访问模型接口，也不核验其他 Harness 账户。缺配置及未记住凭据保持现有语义。
4. 检查延迟、网络失败、超时、未登录、组件缺失或损坏分别显示正确状态；重试成功后当前页面原地恢复，整段检查没有模型调用或组件下载。
5. 多入口和连续重试只产生一个检查；取消、退出、切换配置或账户、恢复数据和迟到结果不能重新启用旧授权或发送旧题目。
6. 共享状态刷新覆盖训练复盘等已打开的面板，保留草稿、答案、滚动与键盘操作；数据加载失败仍进入原恢复流程。

自动化使用假组件、假凭据、mock 账户服务和隔离 profile。系统开机后的首次打开、安装版及真实账户的体验另列人工验收；自动化通过不能替代这些记录，也不包含调用真实收费模型的授权。
